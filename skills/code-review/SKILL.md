# 代码审阅

找到真实、重要、可定位的问题。主审理解整体，帮手从不同角度独立检查，再用代码和实验裁决疑点；不靠多人重复同一句判断提高置信度。

## 1. 确定审阅对象

先读项目约定、改动说明和相关测试，明确预期行为。根据用户给出的对象建立范围：
- **本地未提交改动**：检查工作区、暂存区和相关新增文件。默认审阅全部未提交改动时，以 HEAD 到当前工作区的最终状态（含相关未跟踪文件）判定问题，暂存与未暂存 diff 用于核对覆盖；用户只要求审暂存内容时，以暂存区为准。
- **分支或 PR**：确认目标分支、基线和待审提交；分支比较通常取共同祖先到待审版本，不把目标分支新增内容误算进来。
- **指定文件或整库**：先建立模块图，按关键入口、数据流和风险分批审阅，不把“读过文件名”算作覆盖。

记录提交标识；未提交改动记录所读 diff 与相关文件状态，让主审和帮手看同一版。审阅中代码变化时，重查受影响的结论。范围不明且会改变审查对象时，先问清；不要随手把最近一次提交当成全部任务。

浏览变更清单，找出入口、核心逻辑、调用方、持久化、外部接口和测试之间的联系。先理解作者想解决什么，再判断实现是否满足它。已有项目规则按目录作用域使用。

## 2. 主审与帮手独立检查

主审先顺着关键路径读代码，同时把可独立完成的审查交给 `delegate`。代码审阅通常至少安排一名独立帮手；多模块或高风险改动可安排两到三名，按风险分工，而不是让所有人泛泛“找 bug”。例如：
- **行为与边界**：控制流、异常分支、输入边界、默认值、调用方假设。
- **状态与生命周期**：异步竞态、取消与重试、资源释放、持久化和恢复。
- **接口与信任边界**：协议、版本兼容、权限、外部输入、敏感数据路径。

分工覆盖本次变更的实际风险，小改动不必凑齐所有角色。主审负责端到端路径、模块交界和最终判断，不能只转述帮手报告。

给每个帮手提供完整任务包：
> 审阅目标与版本、改动目的、仓库位置或可读取的材料、基线与 diff 获取方式、相关约定、负责的风险面。独立阅读改动及必要上下文，检查调用方和已有防护。回报候选问题的位置、触发条件、预期与实际行为、影响、证据和待验证点；没有问题也说明实际覆盖。保持源码不变，测试产生的文件使用各自隔离的临时位置。

独立审查阶段提供需求和事实，不预先灌输主审的疑点或结论。帮手无法读取某些材料时补充材料或调整分工；无法委派时由主审继续，交付时简短标明未完成独立复核。

## 3. 沿真实执行路径找问题

从输入进入系统开始，跟踪状态变化、外部调用、输出和清理。重点看“这一处改动会让哪条原本成立的约束失效”，而非仅在 diff 中找可疑语句。

按实际改动选择检查点：
- 分支、循环、空值、索引、单位、编码、时区及边界值是否符合接口约定。
- 异步结果是否可能晚到、重复或乱序；取消后是否仍写状态；重试是否重复产生副作用。
- 新旧数据、协议、配置和调用方是否兼容；出错后能否恢复，资源是否收回。
- 权限检查和数据校验是否处于正确的信任边界；外部内容是否意外进入执行或解释路径。
- 性能问题是否有实际触发规模、调用频率或复杂度依据。

审阅 Agent、聊天或工具系统时，特别留意流式事件拼接、工具调用配对、前后端状态同步、长任务结束与取消、会话切换及历史恢复。只检查变更触及的机制，并从当前实现确认约定，不凭产品名称猜架构。

读相关测试理解契约；存在需要验证的具体风险时，优先用已有定向测试或最小实验核实，必要时再扩大到回归测试、类型检查和构建。缺测试本身不是缺陷证据，要说清缺口可能掩盖的具体行为。

## 4. 交叉验证候选问题

汇总候选并按根因去重。对准备写进最终结论的问题，让另一位未提出该问题的审阅者验证：主审提出的交给帮手，帮手提出的可由主审或另一名帮手验证。可以用 `helper` 续派已有帮手，不必每个疑点都新建代理。

验证任务不是“确认它”，而是“设法推翻它”：
1. 读取准确版本、调用方、已有校验与测试，找能让判断不成立的上下文。
2. 给出真实可达的触发输入或状态；对比基线，判断是新增回归、被改动放大的旧问题，还是与本次改动无关。
3. 能执行就做最小复现；不能执行则给出完整的静态因果链，并指出尚缺的运行证据。
4. 回报“成立／不成立／证据不足”，附代码或实验依据。

主审复查关键证据并裁决分歧，不按投票或代理数量定案。可达的特殊输入和状态同样可以构成严重 bug，不要求问题在所有输入下发生。无关旧问题通常不进入本次发现；范围本来就是整库审计时则按范围处理。

无法坐实的疑点若会影响用户决策，放到简短的待确认项；否则舍弃。没有实际运行的测试不写成通过。

## 5. 交付可处理的发现

先列发现，按严重性排序，再用几句说明审阅范围、验证情况和剩余缺口。每个问题包含：
- **优先级与动作标题**：P0 紧急阻断；P1 高影响、应尽快修复；P2 常规缺陷；P3 低影响但值得修复。优先级依据影响、可达性和恢复成本。
- **准确位置**：当前待审版本的文件与最小相关行段；PR 中使用对应提交的链接或有效的行内位置。
- **触发条件、实际后果与依据**：说明什么情况下发生、为什么是问题，引用必要的调用路径或复现结果。
- **修复方向**：指出应恢复的约束；简单问题可给小补丁建议，复杂问题不要用未经检查的大改写淹没发现。

例如：
> **[P1] 切换会话后忽略旧请求的流式回调** — `src/session.ts:84–91`  
> A 的请求未结束时切换到 B，回调仍写入当前会话，导致 A 的后续片段进入 B。回调捕获请求所属会话，或在写入前校验请求代际。附上定向复现结果或对应的调用路径。

示例只表示写法，位置和行为以实际代码为准。意见一条对应一个根因，不用风格偏好、泛泛最佳实践或机械重复的测试缺口凑数。用户明确要求风格或架构审阅时，建议与缺陷分开。

没有确认问题时直接说明“本轮未发现可确认的缺陷”，并简述覆盖与测试，不强凑发现。默认只给审阅结果，不顺手修改代码；用户要求修复再进入修改与回归。要求发布 GitHub review 时，按当前工具的 pending review → 行内评论 → submit 流程提交，避免重复评论。
