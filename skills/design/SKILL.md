# 设计

从要解决的问题出发，把方案做到能讨论、能验证、能接着实现。文字解释取舍，图示表达关系，原型暴露交互问题；适合可视化的成果尽量让用户直接看到。

## 1. 读懂场景与现状

先利用对话、记忆和已有材料，确定谁在什么情境下要完成什么，以及当前哪里不顺。只追问会改变设计方向的缺项；可逆的小选择先作合理假设并推进。

已有项目先读相关页面、组件、主题、接口和项目约定；有可用界面就用浏览器查看实际流程。辨清哪些是硬约束，哪些只是旧实现。改一个局部功能时沿用已有语言和组件，不顺手重做整个产品。

提炼少量验收条件，让设计可以被检查，例如“新用户能找到入口”“长任务可取消且不会丢失已有结果”“旧数据可逐步迁移”。区分本轮必须解决、暂时不做和需要用户决定的取舍，不把探索变成长篇需求报告。

## 2. 选择方案，说明关键取舍

通常提出一个推荐方案；确有不同路线且会影响成本、体验或演进时，再给一到两个可比较的替代方案。围绕最关键的约束比较，不为凑选项列出明显劣解。

先确定骨架，再做细节：
- **产品与交互**：入口、信息层级、主要任务路径、用户动作、系统反馈、失败后的恢复。
- **界面与视觉**：内容优先级、布局、排版、色彩、密度和组件状态；已有设计系统优先复用。
- **系统与架构**：模块职责、数据流、接口、状态归属、信任边界、失败模式和迁移方式。

这些视角可以组合，不必为每个任务填写整套模板。对 Agent 类产品，按本次范围处理用户意图、计划、工具执行、进度、产物之间的关系，让“进行中、等待输入、失败、取消、完成”可辨认，并让结果有清楚的去向。外部动作的确认放在真正需要决策的位置，而不是到处弹窗。

关键技术不确定性用小实验验证；设计自身的依赖也要落地确认，例如浏览器能否连接预览、宿主是否提供所需接口。大方案先验证最贵或最不可逆的假设，再打磨外观。

## 3. 让方案变成可见成果

选择最能暴露问题的表达方式，而不是默认交付文档：
- **结构、时序、架构**：用 Mermaid、流程图或简洁的交互图，标出边界、方向和关键失败分支。
- **轻量交互或方案比较**：可直接在正文提供自足的 HTML 演示；使用言提供的主题变量，样式与脚本内联，不依赖外部资源。
- **页面或多状态流程**：制作可运行原型，在浏览器里展示主要路径和关键状态；需要截图、真实布局检查或复杂交互时，优先使用可独立访问的本地预览。
- **已有产品改进**：优先在现有项目的预览方式中验证，展示改动所在的真实上下文。用户只要提案时，在临时原型中演示，不直接重写产品源码。

架构设计也可以做成浏览器里的系统地图或时序演示，但不为简单接口决策硬造一个网站。先把正确关系讲清楚，再决定是否需要交互。

原型覆盖一条完整的核心路径，并展示会影响判断的空态、加载、失败或完成状态。按钮要有明确结果，演示数据和模拟行为在相关位置说明；不把静态按钮包装成已实现的业务能力。用接近真实的信息长度和数据形态，避免短占位文案掩盖布局问题。

视觉选择应服务于内容和产品气质：明确主次、控制密度、统一间距与排版，给操作状态清晰反馈。不要把所有内容装进同款卡片，也不靠渐变和装饰冒充信息层级。新设计可以有鲜明方向，改旧设计则首先保持整体一致。

## 4. 在浏览器里检查，而不只看代码

适合浏览器呈现且环境允许时，使用游目打开实际成果。调用前查看当前工具说明，沿现有项目的启动命令或轻量本地服务建立预览；长驻服务放后台，记录可访问地址。直接在正文渲染的 HTML 若不能由浏览器访问，而又需要截图，则另做可访问的原型页面，保持与正文演示的内容和交互一致。独立页面自带必要样式和主题变量默认值，不依赖聊天页面的宿主样式。

检查形成闭环：
1. **打开与观察**：确认页面加载、字体、样式和数据正常，阅读页面快照，检查控制台报错。
2. **走主路径**：实际点击、输入、展开、切换或取消，确认反馈与设计一致；测试一个关键失败或恢复分支。
3. **检查布局**：用接近目标设备的视口查看；面向多尺寸时再查窄屏。留意溢出、遮挡、长文本、滚动、焦点、键盘操作和对比度。
4. **截图复看**：截取关键视口或元素，查看截图中的信息层级与可读性，修正后重新检查和截图。

优先截取用户需要判断的画面，通常一到三张：主界面、关键交互结果、必要的异常态或窄屏效果。每张说明它对应什么状态、展示哪个设计决定；全页长图只在需要整体结构时使用，不代替细节图。

截图来自实际打开的成果：记录页面或原型版本、视口和状态，避免代码已改但仍展示旧截图。交互正确性还要结合实际操作、页面状态或日志判断，不能只凭一张图。在回复中展示工具返回的截图或交付图像文件，不只说“已截图”；需要作为文件交付时保存到本轮卷宗根目录，确认文件存在并使用明确的文件名。

浏览器不可用或对象是原生窗口等无法直接访问的界面时，改用结构图、可访问的局部原型或明确的文字状态说明，简短交代尚未验证的部分。工具受限不必阻断整个设计。

## 5. 用反馈收敛并给出落地路径

主流程与关键状态可见后，按验收条件检查，优先修正逻辑和信息层级，再打磨外观。复杂设计可用 `delegate` 请帮手从任务可完成性、实现代价或失败场景独立挑错；交给它需求、约束和实际原型或图示，不只给一段设计者自己的摘要。

用户有反馈时，找出背后的目标和约束，修改相关部分并复查受影响的路径。局部反馈不自动变成整案推倒重来。

交付通常包括：
- **推荐方案**及最关键的取舍，几句话讲清。
- **可见成果**：按任务提供图示、内联演示或原型；适合且完成浏览器检查时，用关键截图展示效果，标明模拟与已接入部分。
- **落地要点**：需要改动的模块、接口或组件，以及分步实施和验收方式；小设计可以只列下一步。
- **待决定项**：仅留下真正影响方向、成本或风险的问题。

输出长度随任务调整。用户只要设计时，交付方案及足以检验关键判断的图示或原型；用户也要求实现时，再推进生产代码、接入和测试。原型、截图与说明应指向同一版方案。临时脚本和开发材料放本轮草稿目录，只把需要交付的成果放卷宗根目录；预览仍需使用时保留访问方式，清理不再需要且由本轮启动的服务。
